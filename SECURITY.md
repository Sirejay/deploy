# Security Policy

## Supported Versions

Only the latest state of the `main` branch and active production deployment manifests are supported with security updates.

| Version / Branch | Supported |
| --- | --- |
| `main` | :white_check_mark: |
| Older commits / tags | :x: |

## Reporting a Vulnerability

**Please do not report security vulnerabilities through public GitHub issues, discussions, or pull requests.**

If you discover a vulnerability in `SynapsVault/deploy`, `SynapsVault/backend`, `SynapsVault/frontend`, or `SynapsVault/contracts`:

1. **GitHub Private Vulnerability Reporting (Preferred)**: Submit a report via the repository's [Security Advisories](https://github.com/SynapsVault/deploy/security/advisories/new) tab.
2. **Email**: Send a detailed report to `security@synapsvault.xyz` including:
   - Affected component (`k8s/`, `scripts/`, `backend/Dockerfile`, `frontend/Dockerfile`, `.github/workflows/`, or contracts)
   - Reproduction steps or proof-of-concept
   - Potential impact and suggested remediation

### Response SLA

| Milestone | Target SLA |
| --- | --- |
| Initial acknowledgment | Within **48 hours** |
| Triage & severity assessment | Within **5 business days** |
| Remediation & coordinated disclosure | Within **14–30 days** depending on severity |

## Operational Security Guidelines

- **Zero Secrets in Git**: Never commit `.env`, `secrets.env`, `kubeconfig`, Stellar secret keys (`S...`), or unencrypted database dumps. `k8s/secrets.yaml` is strictly a placeholder template and must never be added to `k8s/kustomization.yaml`.
- **Backup Encryption**: Production backups generated by `scripts/backup.sh` must always use `gpg` or `age` encryption (`BACKUP_ENCRYPTION_METHOD` must not be `none` in production).
- **Mainnet Guardrails**: Contract deployments (`scripts/deploy-contracts.cjs`) and database restores (`scripts/restore.sh`) require explicit operator confirmation before modifying live state.
